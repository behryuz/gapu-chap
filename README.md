# gapu-chap — чат с комнатами на Go

Учебный проект по завершению курса Go: сервер чата с комнатами, авторизацией по JWT
и обменом сообщениями в реальном времени через WebSocket.

---

## 1. Функциональность

### Основное
- **Регистрация и вход** — пользователь получает JWT-токен.
- **Комнаты** — создание, список, просмотр, вход (join) и выход (leave).
- **Сообщения в реальном времени** — отправка и получение сообщений в комнате через WebSocket.

### Правила авторизации
- Писать в комнату могут **только авторизованные** пользователи.
- Автор сообщения **всегда берётся из токена**, клиент не может передать имя/ID автора
  (нельзя написать от чужого имени).
- Удалить комнату может **только её создатель** (owner).

### Расширения
| Фича | Описание |
|---|---|
| История сообщений | Загрузка старых сообщений комнаты с курсорной пагинацией |
| Личные сообщения (DM) | Переписка 1-на-1 (реализуется как комната типа `direct`) |
| Статус «онлайн» | Сервер знает, у кого открыто WebSocket-соединение, и рассылает события `presence` |
| Отметка «прочитано» | Для каждого пользователя хранится последнее прочитанное сообщение в комнате |
| Поиск по истории | Полнотекстовый поиск PostgreSQL (`tsvector` + GIN-индекс) |
| Блокировка | Модератор может заблокировать пользователя: он не сможет войти и писать |

## 3. Архитектура

Используется **слоистая (clean) архитектура**: каждый слой зависит только от слоя «ниже»
и только через **интерфейсы**.

```
         HTTP / WebSocket клиент
                   │
┌──────────────────▼──────────────────┐
│  transport (http handlers, ws hub)  │  разбор запросов, JSON, коды ответа
└──────────────────┬──────────────────┘
                   │ интерфейсы сервисов
┌──────────────────▼──────────────────┐
│  service (бизнес-логика)            │  правила: кто может удалить комнату и т.д.
└──────────────────┬──────────────────┘
                   │ интерфейсы репозиториев
┌──────────────────▼──────────────────┐
│  repository (postgres)              │  только SQL, никакой логики
└──────────────────┬──────────────────┘
                   ▼
               PostgreSQL
```

**Ключевые принципы:**
- **Интерфейсы объявляются там, где используются** (в пакете `service` объявлен
  `RoomRepository`, а реализует его `repository/postgres`).
- **Доменные ошибки** (`domain.ErrNotFound`, `domain.ErrForbidden`) — сервис возвращает их,
  а HTTP-слой превращает в `404`, `403` и т.п. Сервис ничего не знает про HTTP.
- **`context.Context`** передаётся первым аргументом во все методы сервисов и репозиториев.
- **Dependency Injection вручную** — все зависимости собираются в `cmd/server/main.go`.
- **Graceful shutdown** — по `SIGINT/SIGTERM` сервер корректно закрывает соединения.

## 4. Модель данных

```sql
users          (id, username UNIQUE, password_hash, role ['user'|'moderator'],
                is_banned, created_at)

rooms          (id, name UNIQUE без учёта регистра, kind ['public'|'direct'], owner_id → users, created_at)

room_members   (room_id → rooms, user_id → users, joined_at,
                last_read_message_id,           -- отметка «прочитано»
                PRIMARY KEY (room_id, user_id))

messages       (id BIGSERIAL, room_id → rooms, author_id → users, body,
                created_at,
                search_vector tsvector GENERATED ALWAYS AS (to_tsvector('simple', body)) STORED)

-- индексы
messages (room_id, id DESC)        -- быстрая история с пагинацией
messages USING GIN (search_vector) -- полнотекстовый поиск
```

**Проектные решения:**
- **DM = комната с `kind = 'direct'`** и ровно двумя участниками. Вся логика сообщений,
  истории, прочитанного и поиска переиспользуется без дублирования.
- **«Прочитано» через `last_read_message_id`**, а не флаг на каждом сообщении: одна строка
  на пару (пользователь, комната) вместо N строк. Количество непрочитанных =
  `COUNT(*) WHERE id > last_read_message_id`.
- **Курсорная пагинация** (`?before=<message_id>&limit=50`) вместо `OFFSET` — не «едет»,
  когда приходят новые сообщения, и работает быстро на больших таблицах.
- **Онлайн-статус хранится в памяти** (в Hub), а не в БД — это временное состояние.

## 5. API

Все защищённые эндпоинты требуют заголовок `Authorization: Bearer <token>`.

### REST

| Метод | Путь | Описание | Доступ |
|---|---|---|---|
| `POST` | `/api/auth/register` | Регистрация `{username, password}` | все |
| `POST` | `/api/auth/login` | Вход → `{token}` | все |
| `GET` | `/api/me` | Текущий пользователь | авторизованные |
| `GET` | `/api/rooms` | Список публичных комнат | авторизованные |
| `POST` | `/api/rooms` | Создать комнату `{name}` | авторизованные |
| `GET` | `/api/rooms/{id}` | Информация о комнате | авторизованные |
| `DELETE` | `/api/rooms/{id}` | Удалить комнату | **только создатель** |
| `POST` | `/api/rooms/{id}/join` | Войти в комнату | авторизованные |
| `POST` | `/api/rooms/{id}/leave` | Выйти из комнаты (создатель не может — только удалить) | участники |
| `GET` | `/api/rooms/{id}/members` | Список участников | авторизованные |
| `POST` | `/api/rooms/{id}/messages` | Отправить сообщение `{body}` (тот же сервис, что и WebSocket) | участники |
| `GET` | `/api/rooms/{id}/messages?before=&limit=` | История сообщений | участники |
| `GET` | `/api/rooms/{id}/messages/search?q=` | Поиск по истории | участники |
| `POST` | `/api/rooms/{id}/read` | Отметить прочитанным `{message_id}` | участники |
| `POST` | `/api/dm/{user_id}` | Открыть (или получить) DM-комнату | авторизованные |
| `GET` | `/api/users/online` | Список онлайн-пользователей | авторизованные |
| `POST` | `/api/moderation/users/{id}/ban` | Заблокировать | **модератор** |
| `POST` | `/api/moderation/users/{id}/unban` | Разблокировать | **модератор** |

Формат ошибки (единый для всех):
```json
{ "error": "room not found" }
```

### WebSocket

Подключение: `GET /ws?token=<jwt>`

> Браузерный `WebSocket` API не умеет отправлять заголовки, поэтому токен передаётся
> в query-параметре. Токен проверяется **один раз при подключении**, после чего
> `userID` и `username` привязываются к соединению — именно они используются как автор
> сообщения. Поле автора от клиента **игнорируется**.

Все сообщения — JSON вида «конверт»:
```json
{ "type": "<тип события>", "payload": { ... } }
```

**Клиент → сервер**

| type | payload | Описание |
|---|---|---|
| `room.subscribe` | `{ "room_id": 1 }` | Начать получать сообщения комнаты (нужно быть участником) |
| `room.unsubscribe` | `{ "room_id": 1 }` | Перестать получать |
| `message.send` | `{ "room_id": 1, "body": "Привет" }` | Отправить сообщение |
| `message.read` | `{ "room_id": 1, "message_id": 42 }` | Отметить прочитанным |

**Сервер → клиент**

| type | payload | Описание |
|---|---|---|
| `message.new` | `{ "id", "room_id", "author": {id, username}, "body", "created_at" }` | Новое сообщение |
| `message.read` | `{ "room_id", "user_id", "message_id" }` | Кто-то прочитал |
| `presence` | `{ "user_id", "username", "online": true }` | Пользователь появился/ушёл |
| `room.deleted` | `{ "room_id" }` | Комната удалена владельцем |
| `room.subscribed` | `{ "room_id" }` | Подтверждение подписки |
| `error` | `{ "message": "..." }` | Ошибка обработки события |

### Как работает WebSocket-часть (паттерн Hub)

```
  REST POST /messages ─┐
                       ▼
  ws: message.send ──► MessageService.Send ──► БД
                       │
                       └─► MessagePublisher.PublishMessage  (интерфейс сервиса)
                                     │
                         ┌───────────▼─────────── Hub (sync.RWMutex) ─┐
                         │ clients map[*Client]struct{}               │
                         │ rooms   map[roomID]map[*Client]struct{}    │
                         └───────────┬────────────────────────────────┘
                                     │ enqueue (без блокировки)
                         ┌───────────▼───┐
                         │ Client        │ readLoop  ◄── сокет (события клиента)
                         │ (1 на conn)   │ writePump ──► сокет (chan send + ping)
                         └───────────────┘
```

- У каждого соединения **две горутины** (через `errgroup`): `readLoop` читает события
  из сокета, `writePump` пишет в сокет из буферизованного канала `send` и шлёт ping.
  Если одна из них завершилась — отменяется контекст и завершается вторая.
- **Hub защищён `sync.RWMutex`**: рассылка (частая операция) берёт read-lock,
  подписка/отписка — write-lock.
- **Сервис не знает про WebSocket**: он зависит от интерфейса `MessagePublisher`, который
  реализует Hub. Поэтому сообщение, отправленное и через REST, и через WebSocket,
  одинаково сохраняется и рассылается.
- Сообщение **сначала сохраняется в БД**, и только потом рассылается — у него есть `id`
  и `created_at`, история и real-time не расходятся.
- Если канал `send` клиента переполнен (медленный клиент) — соединение закрывается
  (`StatusPolicyViolation`), чтобы не тормозить остальных.
- Ping раз в 30 секунд для обнаружения «мёртвых» соединений.
- При остановке сервера Hub закрывает все соединения со статусом `GoingAway`
  (`http.Server.RegisterOnShutdown`).
- Ограничение: Hub живёт в памяти одного процесса. Для нескольких инстансов сервера
  нужен общий брокер (Redis Pub/Sub, PostgreSQL `LISTEN/NOTIFY`).

## 6. Запуск

```bash
cp .env.example .env
docker compose up -d          # PostgreSQL
make migrate-up               # применить миграции
make run                      # запустить сервер на :8080
```

Переменные окружения:

| Переменная | Пример | Описание |
|---|---|---|
| `HTTP_ADDR` | `:8080` | Адрес сервера |
| `DATABASE_URL` | `postgres://chat:chat@localhost:5432/chat?sslmode=disable` | Подключение к БД |
| `JWT_SECRET` | `change-me` | Секрет для подписи токенов |
| `JWT_TTL` | `24h` | Время жизни токена |

Проверка WebSocket вручную:
```bash
# brew install websocat
websocat "ws://localhost:8080/ws?token=<TOKEN>"
{"type":"room.subscribe","payload":{"room_id":1}}
{"type":"message.send","payload":{"room_id":1,"body":"Привет!"}}
```

## 8. Безопасность (чек-лист)

- Пароли только в виде bcrypt-хеша, никогда не логируются и не возвращаются в API.
- JWT подписывается HMAC-SHA256; при проверке **явно проверяется алгоритм** (защита от `alg: none`).
- В токен кладутся только `uid` (user ID), `username`, `role`, `iat`, `exp`.
- Автор сообщения — только из контекста/соединения, никогда из тела запроса.
- Все SQL-запросы параметризованные (`$1, $2`) — защита от SQL-инъекций.
- Ограничения: длина сообщения (например, 4000 символов), размер WebSocket-фрейма
  (`conn.SetReadLimit`), лимит `limit` в пагинации.
- Заблокированный пользователь: логин запрещён, а активные WS-соединения закрываются.
